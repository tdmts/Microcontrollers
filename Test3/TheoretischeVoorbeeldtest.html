Vraag 1: de stappentabel (meerkeuze)

Een student stuurt een stappenmotor aan in full step. De twee spoelen hangen elk over één brug van een L293D, en in TinkerCAD staan er vier anti-parallelle leds op de plaats van de spoelen. Zijn stappentabel ziet er zo uit.

const int motorPinnen[] = {2, 3, 4, 5};

const int volleStap[4][4] = {
  {1, 0, 0, 0}, // spoel A, ene richting
  {0, 1, 0, 0}, // spoel A, andere richting
  {0, 0, 1, 0}, // spoel B, ene richting
  {0, 0, 0, 1}  // spoel B, andere richting
};

void zetStap(int stap)
{
  for (int pin = 0; pin < 4; pin++)
  {
    digitalWrite(motorPinnen[pin], volleStap[stap][pin]);
  }
}

Hij doorloopt die vier rijen na elkaar en begint dan opnieuw. Wat ziet hij aan zijn vier leds?

  1. De leds lichten in de rondte op. De motor draait zoals het hoort.
  2. De leds lichten om de beurt van links naar rechts op. De rotor trilt heen en weer in plaats van rond te draaien.
  3. Er brandt nooit een led, want er staat per rij maar één 1.
  4. Alle vier de leds branden flauw, want de rijen volgen elkaar te snel op.
Antwoord op vraag 1

Antwoord: b) De rotor trilt heen en weer.

De volgorde van de rijen klopt niet. Deze tabel doet eerst spoel A in beide richtingen en daarna spoel B in beide richtingen, terwijl je bij full step telkens van spoel moet wisselen: A, B, A, B.

Reken de standen na. Spoel A in de ene richting trekt de rotor naar 0 graden, spoel A in de andere richting naar 180 graden, spoel B in de ene richting naar 90 en spoel B in de andere naar 270. Deze tabel stuurt de rotor dus naar 0, dan 180, dan 90, dan 270. Hij springt heen en weer over de as in plaats van een rondje te maken.

De juiste tabel wisselt om de stap van spoel.

const int volleStap[4][4] = {
  {1, 0, 0, 0}, // spoel A, ene richting
  {0, 0, 1, 0}, // spoel B, ene richting
  {0, 1, 0, 0}, // spoel A, andere richting
  {0, 0, 0, 1}  // spoel B, andere richting
};

Antwoord c) klopt niet, want één 1 per rij is juist wat one phase full step betekent: er staat telkens één spoel onder spanning. Bij half step staan er in de helft van de rijen twee enen, en dan gaat de rotor tussen twee standen in staan.

Vraag 2: interrupts en de ISR (meerdere juiste antwoorden)

Welke van onderstaande uitspraken zijn juist? Er zijn er meerdere juist.

  1. Op een Arduino UNO kunnen alleen pin 2 en pin 3 een interrupt opwekken.
  2. Een variabele die je zowel in je ISR als in je loop() gebruikt, moet volatile zijn.
  3. delay(500) in een ISR wacht een halve seconde en gaat daarna gewoon verder.
  4. millis() lezen in een ISR levert een bruikbare waarde op, ook al staat de klok stil zolang je erin zit.
  5. Een Wire.requestFrom() in een ISR geeft je een foutmelding of een timeout, zodat je het probleem meteen ziet.
Antwoord op vraag 2

Antwoord: a, b en d zijn juist. c en e zijn fout.

  • a) juist. De rest van je pinnen kan het niet. Zet je je knop toch elders, dan geeft digitalPinToInterrupt() de waarde NOT_AN_INTERRUPT terug en negeert attachInterrupt() dat stilzwijgend. Je code compileert, uploadt en doet nooit iets.
  • b) juist. Zonder volatile mag de compiler de waarde in de processor bijhouden in plaats van ze telkens uit het geheugen te halen. Hij ziet je ISR nergens opgeroepen worden, dus hij ziet het verband niet, en je loop() blijft een verouderde kopie lezen. De compiler waarschuwt daar nooit voor.
  • c) fout. Je bord hangt. delay() telt de tijd af met een timer die zelf een interrupt gebruikt, en die staat uit zolang jouw ISR draait. De tijd staat dus stil en delay() raakt nooit klaar. Alleen de resetknop helpt nog.
  • d) juist. Je krijgt de waarde van vlak voor de onderbreking, en dat is nauwkeurig genoeg voor een vraag als "is het al 200 ms geleden?". Daar draait de ontdendering van een interrupt op. Een tijdsduur meten binnen één ISR lukt er niet mee, want tussen twee oproepen zit dan geen tijd.
  • e) fout. Dit is de gemeenste van allemaal, want er komt geen enkele melding. De I²C-hardware gebruikt zelf een interrupt om na elke byte verder te gaan, en die staat uit. Wire.requestFrom() blijft dus eeuwig op hulp wachten die nooit komt, zonder timeout. Zet in plaats daarvan een vlag en doe je I²C-werk in de loop().

Vraag 3: een boodschap over de lijn (open vraag)

Een Arduino die de temperatuur meet, stuurt zijn meting door naar een tweede Arduino met deze regel.

Serial.println("TEMP:21");
  1. Hoeveel bytes gaan er over de lijn, en welke waarden hebben ze? Gebruik dat '0' gelijk is aan 48 en 'A' aan 65.
  2. Schrijf de code waarmee de ontvanger daar de sleutel TEMP en het getal 21 uit haalt.
  3. Waarom hoort daar een trim() in, en waarom een test op het resultaat van indexOf()?
Antwoord op vraag 3

1. Negen bytes

De tekst zelf is zeven tekens lang, en println() plakt er nog '\r' (13) en '\n' (10) achter.

Wat er echt over de lijn gaat
Teken T E M P : 2 1 \r \n
Waarde 846977805850491310

De hoofdletters staan op een rij vanaf 'A' = 65, dus T is de twintigste letter en komt op 65 + 19 = 84. De cijfers staan op een rij vanaf '0' = 48, dus '2' is 50 en '1' is 49. Merk op dat het getal 21 als twee tekens vertrekt en niet als de byte 21.

2. De ontvanger

void loop()
{
  if (Serial.available() > 0)
  {
    String regel = Serial.readStringUntil('\n');
    regel.trim();

    int scheiding = regel.indexOf(':');

    if (scheiding > 0)
    {
      String sleutel = regel.substring(0, scheiding);
      String waarde = regel.substring(scheiding + 1);

      if (sleutel == "TEMP")
      {
        int temperatuur = waarde.toInt();

        Serial.println(temperatuur);
      }
    }
  }
}

3. De twee vangnetten

readStringUntil('\n') leest tot en met de line feed, maar de carriage return die daarvoor stond zit nog in je String. Zonder trim() is je waarde dus "21\r". Bij toInt() valt dat toevallig weg, maar een vergelijking als waarde == "AAN" mislukt dan zonder dat je ziet waarom.

indexOf() geeft -1 terug wanneer het teken er niet in staat. Ga je dan toch verder, dan rekent substring(0, -1) met onzin. Op een seriële lijn komt er vroeg of laat rommel binnen, dus die test is geen luxe. Er staat > 0 en niet >= 0, want een lijn die met een dubbelepunt begint heeft wel een scheidingsteken maar geen sleutel.

Vraag 4: de basisweerstand berekenen (numeriek)

Je schakelt een DC motor met een P2N2222A. De motor trekt 120 mA. In de datasheet lees je een hFE van ongeveer 200 en een Vbe van 0,7 V. Je stuurt de transistor vanaf een gewone uitgangspin, die 5 V geeft.

  1. Met welke hFE reken je verder, en waarom die en niet de 200 uit de datasheet?
  2. Bereken de basisstroom Ib.
  3. Bereken de basisweerstand Rb en kies er een standaardwaarde bij.
  4. Leg uit waarom deze motor sowieso niet rechtstreeks aan een uitgangspin mag.
Antwoord op vraag 4

1. hFE = 40

Je deelt de hFE uit de datasheet ruim door, hier door 5. Reken je met 200, dan stuur je precies genoeg basisstroom om die 120 mA te halen als alles meezit, en dat is te krap: de hFE verschilt sterk van exemplaar tot exemplaar, zakt bij hogere stroom en verandert met de temperatuur. Bovendien wil je dat de transistor in saturatie gaat en dus volledig openstaat, want een transistor die maar half openstaat verstookt het verschil als warmte.

2. Ib = 3 mA

De collectorstroom is de stroom door je motor, dus 120 mA of 0,12 A.

Ib = 0,12 A / 40 = 0,003 A = 3 mA

3. Rb = 1433 Ω, dus 1,5 kΩ

Over de basisweerstand staat de spanning van je pin min de spanning over de basis-emitterjunctie, dus 5 V min 0,7 V = 4,3 V.

Rb = 4,3 V / 0,003 A = 1433 Ω

Die waarde bestaat niet als standaardweerstand. De dichtstbijzijnde is 1,5 kΩ. Je rondt daarmee naar boven af en stuurt dus iets minder basisstroom dan berekend, en dat mag, want in die 3 mA zat al een marge van factor 5. Zit je twijfelachtig dicht bij de grens, kies dan de kleinere weerstand: te veel basisstroom is zelden een probleem, te weinig wel.

4. Drie keer over de grens

Een pin van de UNO levert veilig zo'n 20 mA en mag er absoluut maximaal 40 aan. Die 120 mA is daar het drievoud van, dus de pin gaat stuk voor de motor draait. Daarnaast zit er nog een tweede reden: een motor is een spoel, en op het moment dat je hem uitschakelt wekt die een spanningspiek op die de pin evengoed vernielt. Daarvoor staat de vrijloopdiode over de motor.

Vraag 5: zoek de drie fouten (code)

Een student telt hoe vaak er op een knop gedrukt wordt. De knop hangt met een pull-upweerstand aan de Arduino en trekt de pin laag bij een druk. De schakeling is correct gebouwd, en met een gewone digitalRead() in de loop() werkte alles.

Sinds hij op interrupts is overgestapt, gebeurt er helemaal niets meer. De monitor blijft leeg, hoe vaak hij ook drukt.

const int knopPin = 7;
const int ledPin = 8;

bool knopGedrukt = false;

int aantal = 0;

void knopISR()
{
  knopGedrukt = true;

  Serial.println("Er is gedrukt");
}

void setup()
{
  pinMode(ledPin, OUTPUT);
  pinMode(knopPin, INPUT_PULLUP);

  Serial.begin(9600);

  attachInterrupt(digitalPinToInterrupt(knopPin), knopISR, FALLING);
}

void loop()
{
  if (knopGedrukt == true)
  {
    knopGedrukt = false;

    aantal++;

    digitalWrite(ledPin, aantal % 2);

    Serial.println(aantal);
  }
}

Er zitten drie fouten in. Welke, en hoe los je ze op?

Antwoord op vraag 5

Fout 1: de knop hangt op pin 7

Op een UNO kunnen alleen pin 2 en pin 3 een interrupt opwekken. Voor pin 7 geeft digitalPinToInterrupt() de waarde NOT_AN_INTERRUPT terug, en attachInterrupt() negeert die zonder iets te zeggen. Dat verklaart precies wat de student ziet: alles compileert en uploadt, en er gebeurt nooit iets.

Oplossing: verhuis de knop naar pin 2 of pin 3.

const int knopPin = 2;

Zolang die ISR nooit afgaat, merk je ook niets van wat erin staat. De twee andere fouten komen dus pas boven zodra deze opgelost is.

Fout 2: knopGedrukt is geen volatile

De variabele wordt in de ISR geschreven en in de loop() gelezen, dus ze moet volatile zijn. Zonder dat woord mag de compiler de waarde in de processor bijhouden in plaats van ze telkens opnieuw uit het geheugen te halen, want hij ziet nergens dat die ISR opgeroepen wordt. Je loop() blijft dan naar een verouderde kopie kijken.

Dit is de gevaarlijkste van de drie: er komt geen waarschuwing, en het werkt vaak wel tot je iets kleins verandert en de compiler anders beslist.

volatile bool knopGedrukt = false;

Fout 3: er wordt geprint vanuit de ISR

Serial.println() hoort niet thuis in een ISR. Bij 9600 baud duurt één teken ruim een milliseconde, en normaal geeft je Arduino die tekens beetje bij beetje weg terwijl je programma verder loopt. In een ISR kan dat niet, dus zit je vast te schrijven terwijl alles stilligt: je mist knopdrukken en je klok loopt achter.

Oplossing: haal die regel weg. De loop() print het aantal toch al, en daar dient het vlagpatroon voor.

void knopISR()
{
  knopGedrukt = true;
}
Op echte hardware blijft er nog werk over

Ook met deze drie fouten weg telt de teller op een fysieke knop te snel, want een drukknop stuitert en je ISR gaat dan vijf tot twintig keer af per druk. Daar zet je een vergrendeling van 200 ms tegen. In TinkerCAD zie je dat probleem nooit, want de knop daar maakt precies één keer contact.
