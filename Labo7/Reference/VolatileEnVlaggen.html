volatile en de vlagvariabele

Je ISR moet kort blijven, maar er moet wél iets gebeuren. De oplossing is dat je ISR alleen een boodschap achterlaat en je loop() het echte werk doet. Hier lees je hoe je die boodschap doorgeeft zonder ze onderweg kwijt te spelen.

Waarom volatile

Een variabele die je zowel in je ISR als in je loop() gebruikt, moet volatile zijn:

volatile bool knopGedrukt = false;

Waarom? Omdat de compiler slim is, en die slimheid hier tegen je werkt.

Wanneer de compiler ziet dat je in je loop() steeds opnieuw dezelfde variabele uitleest, denkt hij: die verandert hier toch nergens, ik hou hem gewoon even bij in de processor zelf, dat is sneller dan hem telkens uit het geheugen te halen. Vaak is dat precies de juiste beslissing.

Maar jouw variabele verandert wel degelijk: in je ISR. En die ISR staat nergens in je loop(), dus de compiler ziet het verband niet. Het gevolg is een loop() die eeuwig naar een verouderde kopie zit te kijken en nooit merkt dat de knop ingedrukt is.

volatile is jouw manier om te zeggen: ga er niet van uit dat je weet wanneer dit verandert, haal hem elke keer opnieuw op.

Je krijgt hier geen waarschuwing over

Vergeet je volatile, dan compileert alles netjes. Erger nog: het werkt vaak ook gewoon, tot je iets kleins verandert en de compiler ineens besluit om wél een kopie bij te houden. Dan lijkt het alsof een onschuldige aanpassing je programma gesloopt heeft.

Regel: elke variabele die je in een ISR aanraakt, krijgt volatile. Zonder uitzondering.

Het vlagpatroon

Dit is het belangrijkste patroon van het hele labo, en je gaat het in bijna elke oefening gebruiken.

Het idee: je ISR doet niets anders dan een bool op true zetten. Zo'n variabele heet een vlag. Je loop() kijkt of die vlag omhoog staat, doet dan het echte werk, en zet ze weer omlaag.

const int knopPin = 2;
const int ledPin = 8;

volatile bool knopGedrukt = false;

bool ledBrandt = false;

// De ISR: zo kort als het maar kan
void knopISR()
{
  knopGedrukt = true;
}

void setup()
{
  pinMode(ledPin, OUTPUT);
  pinMode(knopPin, INPUT_PULLUP);

  Serial.begin(9600);

  attachInterrupt(digitalPinToInterrupt(knopPin), knopISR, FALLING);
}

void loop()
{
  if (knopGedrukt == true)
  {
    knopGedrukt = false; // eerst de vlag neerhalen

    ledBrandt = !ledBrandt;
    digitalWrite(ledPin, ledBrandt);

    Serial.println("Er is gedrukt"); // dit mag hier wel, in de ISR niet
  }
}

Kijk wat je hiermee wint. Het printen, dat in een ISR verboden is, staat nu in de loop() en mag dus. Hetzelfde geldt voor een Wire-opdracht, een delay(), of eender wat dat te lang duurt. Je ISR blijft één regel.

Haal de vlag neer vóór je aan het werk gaat

Zet knopGedrukt = false; bovenaan, niet onderaan. Doe je het op het einde, dan wis je ook een druk die net tijdens je werk binnenkwam, en die druk is dan voorgoed weg.

Zet je ze bovenaan en komt er tijdens je werk een nieuwe druk binnen, dan zet de ISR de vlag gewoon opnieuw en handel je die de volgende ronde af. In het slechtste geval doe je één keer overbodig werk. Dat is een pak beter dan iets missen.

Een getal van vier bytes heeft meer nodig

Bij een bool of een byte hoef je verder niets te doen. De processor haalt zo'n waarde met één instructie uit het geheugen, en een instructie kan niet halverwege onderbroken worden.

Bij een int (twee bytes) of een long (vier bytes) ligt dat anders. Die haalt de processor stuk voor stuk op, en tussen die stukjes door kan je ISR toeslaan.

Een getal dat nooit bestaan heeft

Stel: je teller staat op 255 en je ISR telt hem op naar 256. In het geheugen zijn dat twee bytes.

  1. Je loop() leest de onderste byte: 255.
  2. De ISR slaat toe en telt op. De onderste byte wordt 0, de bovenste wordt 1.
  3. Je loop() leest de bovenste byte: 1.

Je loop() plakt die twee samen tot 511. Niet 255, niet 256, maar een getal dat op geen enkel moment in je programma bestaan heeft. En het gebeurt maar zelden, dus je vindt het pas na een halve dag zoeken.

De oplossing is de interrupts heel eventjes uitzetten terwijl je het getal ophaalt:

const int knopPin = 2;

volatile unsigned long aantalDrukken = 0;

unsigned long vorigAantal = 0;

void knopISR()
{
  aantalDrukken++;
}

void setup()
{
  pinMode(knopPin, INPUT_PULLUP);

  Serial.begin(9600);

  attachInterrupt(digitalPinToInterrupt(knopPin), knopISR, FALLING);
}

void loop()
{
  noInterrupts();                        // even niet storen
  unsigned long aantal = aantalDrukken;  // vier bytes in een keer overnemen
  interrupts();                          // en meteen weer aan

  if (aantal != vorigAantal)
  {
    vorigAantal = aantal;

    Serial.println(aantal);
  }
}

Je maakt dus razendsnel een kopie, en werkt daarna verder met die kopie. Tussen noInterrupts() en interrupts() staan zo weinig mogelijk regels: zet je er je Serial.println() ook nog tussen, dan heb je precies het probleem gemaakt dat je wou vermijden.

Raak je zo geen drukken kwijt?

Nee. Drukt iemand op de knop terwijl de interrupts uitstaan, dan onthoudt de hardware dat. Zodra interrupts() uitgevoerd is, gaat je ISR alsnog af. Je verliest hoogstens een paar microseconden.

Eén vuistregel om alles simpel te houden

Alleen de ISR schrijft, de loop leest

Zorg dat je gedeelde variabelen maar op één plaats aangepast worden. De ISR telt op, de loop() kijkt alleen. Ga je in je loop() ook aantalDrukken++ schrijven, dan heb je hetzelfde probleem opnieuw, want optellen is stiekem drie stappen: ophalen, plus één, terugzetten. En daar kan de ISR net zo goed tussen springen.

De enige uitzondering is een vlag die je in de loop() neerhaalt. Dat is één byte, dus één instructie, en dus veilig.
