Denderen bij een interrupt

Je bouwt een teller die optelt bij elke druk op de knop. Je drukt één keer, en de teller springt naar 6. Je code klopt nochtans. Wat er gebeurt is dendering, en bij een interrupt is ze veel vervelender dan bij pollen.

Wat er gebeurt

Een drukknop is een stuk veerend metaal. Duw je erop, dan stuitert hij een paar keer heen en weer voor hij tot rust komt. Dat duurt maar een paar milliseconden, maar in die tijd gaat de spanning op je pin vijf tot twintig keer op en neer.

Je kent dit al uit Debouncen. Bij pollen viel het nog mee, want je loop() kijkt maar af en toe, en met een korte delay() na een verandering was je ervan af.

Bij een interrupt ligt dat anders. De hardware mist geen enkele flank, dat is nu net waar je hem voor gekozen hebt. Elk van die stuiteringen is een dalende flank, en dus gaat je ISR er allemaal een keer voor af.

Herken je dit?
  • Je teller springt met sprongen van 3 tot 10 tegelijk.
  • Je led die moet omschakelen, doet soms wel en soms niets. (Logisch: bij een even aantal flanken sta je weer waar je begon.)
  • Je stuurt één boodschap over de seriële lijn en er komen er zeven aan.

Dat is dendering. Je code is niet fout, je knop is geen ideale schakelaar.

De oplossing: een vergrendeling

Je kan het stuiteren niet tegenhouden, maar je kan het wel negeren. Onthoud wanneer je de vorige druk aanvaard hebt, en negeer alles wat binnen de volgende 200 milliseconden nog binnenkomt.

Een mens kan onmogelijk vijf keer per seconde bewust drukken, dus je verliest niets. Het gestuiter is na een paar milliseconden voorbij, dus je vangt alles op.

Waarom hier 200 ms en bij het pollen 50 ms

Bij het pollen vergelijk je de huidige stand met de vorige. Indrukken is HIGH naar LOW, loslaten is LOW naar HIGH, en dat zijn twee verschillende overgangen. Je delay() hoeft daar dus alleen het gestuiter zelf te overleven, en 50 ms is daarvoor ruim genoeg.

Hier telt je vergrendeling vanaf het indrukken, terwijl ook het loslaten dalende flanken oplevert. Ze moet dus de hele beweging overbruggen, en een gewone tik duurt al snel meer dan 100 ms. Vandaar het hogere getal.

De twee constanten heten daarom anders. Bij het pollen gebruik je ontdenderTijd van 50 ms, de constante die je uit Debouncen kent. Bij een interrupt gebruik je vergrendelTijd van 200 ms.

const int knopPin = 2;
const int ledPin = 8;

const unsigned long vergrendelTijd = 200; // zolang negeren we nieuwe flanken

volatile bool ledBrandt = false;
volatile unsigned long laatsteDruk = 0;

void knopIngedrukt()
{
  unsigned long nu = millis();

  if (nu - laatsteDruk < vergrendelTijd)
  {
    return; // dit is gestuiter, geen nieuwe druk
  }

  laatsteDruk = nu;

  ledBrandt = !ledBrandt;
  digitalWrite(ledPin, ledBrandt);
}

void setup()
{
  pinMode(ledPin, OUTPUT);
  pinMode(knopPin, INPUT_PULLUP);

  attachInterrupt(digitalPinToInterrupt(knopPin), knopIngedrukt, FALLING);
}

void loop()
{
}

De return stapt meteen uit de ISR, en dat is de goedkoopste manier om een flank weg te gooien.

Mag millis() dan wel in een ISR?

In De regels van een ISR staat dat de klok van millis() stilstaat zolang je in een ISR zit, en dat klopt.

Maar hier hoeft die klok niet verder te lopen. Je wil alleen weten hoe laat het was op het moment dat je onderbroken werd, en dat is wat je krijgt. Tussen twee knopdrukken in draait je loop(), dus tegen de tijd dat je ISR opnieuw afgaat staat de klok weer verder.

Voor een vergrendeling van 200 ms is dat ruim nauwkeurig genoeg. Je zou hem alleen niet moeten gebruiken om binnen één ISR een tijdsduur te meten, want daar staat hij inderdaad stil.

Waar deze oplossing nog tekortschiet

Er is één geval waarin de vergrendeling het laat afweten, namelijk wanneer je de knop lang ingedrukt houdt.

Ook bij het loslaten stuitert een knop. Houd je hem een seconde vast, dan is de eerste flank van dat losgelaten-gestuiter meer dan 200 ms na je druk, en wordt hij dus aanvaard als een tweede druk. Je led schakelt terug om.

In de praktijk valt dat vaak mee, omdat de meeste knoppen bij het loslaten veel minder stuiteren dan bij het indrukken. Merk je het toch, dan zijn er twee wegen:

  • De vergrendeling langer maken, bijvoorbeeld 500 ms. Dat is snel gedaan, maar dan reageert je knop trager.
  • De interrupt alleen gebruiken om je loop() wakker te maken, en de eigenlijke ontdendering met de toestandsmethode uit Debouncen in je loop() doen. Meer werk, maar volledig sluitend.
In TinkerCAD zie je hier niets van

De drukknop in TinkerCAD maakt precies één keer contact en stuitert nooit. Je vergrendeling lijkt daar dus overbodige code die niets doet.

Laat ze staan. Op een echt bord verdient ze zich meteen terug, en dat je het probleem in de simulator niet ziet, maakt het net gevaarlijker, want je zou anders pas op het labo ontdekken dat je teller nergens op slaat.

Samengevat

Ontdenderen bij een interrupt
  • Elke stuitering is een flank, en dus een oproep van je ISR.
  • Onthou met millis() wanneer je de vorige druk aanvaardde.
  • Komt er binnen de 200 ms een nieuwe, stap dan meteen uit de ISR met return.
  • Die tijdsvariabele is volatile, net als al de rest die je ISR aanraakt.
  • Test op echte hardware, niet alleen in TinkerCAD.
