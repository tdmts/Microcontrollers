Noodstop over de seriële lijn

De machine staat op de ene Arduino, de noodknop op de andere. Alles wat je dit labo geleerd hebt komt hier samen, en je ontdekt de grens ervan: een interrupt bij de zender helpt niets zolang de ontvanger vastzit.

Dit is de laatste oefening van het labo. Je brengt de seriële verbinding uit labo 6 samen met de interrupts van dit labo.

Deze oefening werk je uit in TinkerCAD, met twee Arduino's.

Wat je moet programmeren

  1. Arduino 1 laat een looplicht lopen over zijn vier leds.
  2. Arduino 2 heeft een noodstopknop op een interrupt. Wordt die ingedrukt, dan stuurt hij STOP over de lijn.
  3. Arduino 1 ontvangt dat, dooft alle leds, en blijft gestopt.

De eerste valkuil: niet zenden vanuit je ISR

Het lijkt logisch om die Serial.println("STOP") gewoon in je ISR te zetten. Dan gebeurt het meteen, en dat wil je toch bij een noodstop?

Doe het niet. Bij 9600 baud duurt één teken ruim een milliseconde. Vijf tekens plus de regelovergang is dus al gauw zeven milliseconden waarin je ISR niets anders doet dan wachten, en waarin je hele controller stilligt. Zie De regels van een ISR.

Je ISR zet dus een vlag, en je loop() verstuurt. Precies zoals bij de expander.

De tweede valkuil: en dan komt hij toch te laat aan

Bouw eerst de voor de hand liggende versie. Arduino 1 draait het looplicht dat je in Noodstop op je looplicht geschreven hebt, met zijn delay(250), en kijkt bovenaan zijn loop() of er iets binnengekomen is.

Druk nu op de noodstop en let goed op wanneer de leds doven.

Je interrupt heeft je hier niets opgeleverd

Arduino 2 reageert inderdaad meteen: zijn ISR gaat af binnen enkele microseconden en het bericht staat op de lijn voor je vinger van de knop is.

Maar Arduino 1 zit in delay(250). Het bericht wacht netjes in zijn ontvangstbuffer, en pas wanneer die delay() afgelopen is kijkt hij ernaar. Je noodstop is dus nog altijd tot een kwart seconde te laat, ook al is de knop zelf perfect.

Een interrupt versnelt alleen het bord waar hij op staat. Zit de ontvanger vast, dan sta je nergens.

Arduino 1 moet dus zijn delay() opgeven. In plaats van te wáchten tot het tijd is voor de volgende led, blijft hij rondjes draaien en kijkt hij telkens of het al tijd is.

Wachten zonder delay

Het recept: onthou met millis() wanneer je iets voor het laatst gedaan hebt, en doe het opnieuw zodra er genoeg tijd verstreken is.

unsigned long vorigeStap = 0;
const unsigned long stapDuur = 250;

void loop()
{
  // hier draait je loop duizenden keren per seconde door

  if (millis() - vorigeStap >= stapDuur)
  {
    vorigeStap = millis();

    // en dit gebeurt maar vier keer per seconde
  }
}

Je loop() blijft nu volledig vrij. Alles wat je er verder in zet, wordt duizenden keren per seconde bekeken in plaats van vier keer.

Je kent dit patroon al uit Teller met I²C-drukknoppen, waar je teller op dezelfde manier op tijd liep zonder de knoppen doof te maken.

Kon Arduino 1 dan zelf geen interrupt gebruiken?

Voor de seriële lijn heeft hij er al eentje, alleen niet eentje van jou. Binnenkomende tekens worden door de hardware zelf met een interrupt opgevangen en in de buffer gezet, ook terwijl je in een delay() zit. Daarom raakt je bericht nooit verloren.

Maar die interrupt zet het alleen kláár. Wat er méé moet gebeuren, blijft aan jouw loop(), en die moet er dus tijd voor hébben.

Oplossing

Arduino 1, de machine met het looplicht:

Geen enkele delay() meer. De loop() draait vrij rond en doet twee dingen: kijken of er post is, en kijken of het tijd is voor de volgende led.

const int leds[] = {3, 4, 5, 6};
const int aantalLeds = 4;

const unsigned long stapDuur = 250;

unsigned long vorigeStap = 0;
int huidigeLed = 0;
bool gestopt = false;

void allesUit()
{
  for (int i = 0; i < aantalLeds; i++)
  {
    digitalWrite(leds[i], HIGH); // sinking: HIGH is uit
  }
}

void setup()
{
  for (int i = 0; i < aantalLeds; i++)
  {
    pinMode(leds[i], OUTPUT);
  }

  allesUit();

  Serial.begin(9600);

  // Komt er ooit een halve lijn binnen, dan blijven we hier hoogstens 50 ms
  // op de rest wachten in plaats van een volledige seconde.
  Serial.setTimeout(50);
}

void loop()
{
  if (Serial.available() > 0)
  {
    String regel = Serial.readStringUntil('\n');
    regel.trim();

    if (regel == "STOP")
    {
      gestopt = true;
      allesUit();
    }
  }

  if (gestopt == true)
  {
    return; // het looplicht start niet meer opnieuw
  }

  if (millis() - vorigeStap >= stapDuur)
  {
    vorigeStap = millis();

    digitalWrite(leds[huidigeLed], HIGH); // de vorige uit

    huidigeLed++;

    if (huidigeLed >= aantalLeds)
    {
      huidigeLed = 0;
    }

    digitalWrite(leds[huidigeLed], LOW); // de volgende aan
  }
}

Arduino 2, de bedieningspost met de noodstop:

const int noodstopPin = 2;

volatile bool noodstopGedrukt = false;

// Alleen een vlag zetten. Zenden duurt milliseconden, en dat hoort niet
// in een ISR thuis.
void noodstopISR()
{
  noodstopGedrukt = true;
}

void setup()
{
  pinMode(noodstopPin, INPUT_PULLUP);

  Serial.begin(9600);

  attachInterrupt(digitalPinToInterrupt(noodstopPin), noodstopISR, FALLING);
}

void loop()
{
  if (noodstopGedrukt == true)
  {
    noodstopGedrukt = false;

    Serial.println("STOP");

    delay(200);              // laat de dendering uitsterven
    noodstopGedrukt = false; // die dendering heeft de vlag intussen opnieuw gezet
  }
}
Waarom de vlag twee keer neergehaald wordt

De eerste keer is de gewone regel: haal de vlag neer vóór je aan het werk gaat, zodat je een druk die tijdens je werk binnenkomt niet kwijtspeelt.

Maar tijdens die delay(200) stuitert je knop, gaat je ISR nog een paar keer af, en staat de vlag er weer. Zonder die tweede regel stuur je dus alsnog vier keer STOP. Vandaar dat je hem nog eens neerhaalt, ná het stuiteren.

Meet eens hoeveel je gewonnen hebt

Zet in de versie met delay(250) een teller die bijhoudt hoe vaak loop() per seconde draait. Je komt op 4 uit.

In deze versie kom je op tienduizenden uit. Dat is de winst: niet dat er sneller iets gebeurt, maar dat je programma tienduizenden keren per seconde beschikbaar is voor wat er ook binnenkomt. Een delay() geeft die beschikbaarheid weg, en dat merk je pas wanneer er iets dringends is.

Waar je dit labo op neerkomt
  • Een interrupt zorgt dat je een gebeurtenis nooit míst.
  • Het vlagpatroon zorgt dat je ISR kort blijft en je het echte werk toch gedaan krijgt.
  • Maar een interrupt maakt een loop() die vaststaat niet sneller. Wil je dat je programma ook echt réágeert, dan moet het beschikbaar zijn, en dus geen delay() gebruiken.

Die drie samen zijn wat een programma van "het werkt meestal" naar "het werkt altijd op tijd" brengt.
